HyperShape.Optimizers — Module
HyperShape.Optimizers

Optimisers for problems with a box-bounded design vector z and one linear (volume) constraint.

The module is independent of finite elements: an optimiser sees vectors, bounds and an oracle (see AbstractOracle). A new optimiser is a subtype of Optimizer that implements the four functions of the contract:

state = init(opt, z, oracle)            # memory and history
info  = step!(opt, state, z, oracle, ctx) # overwrites z with the next design, returns a StepInfo
reset!(opt, state)                      # forget the history (continuation jump, remeshing)
shrink!(opt, state, factor)             # roll back the last step and reduce the next one
source
HyperShape.Optimizers.AbstractOracle — Type
AbstractOracle

What an optimiser may ask about the problem. Methods to implement for a subtype O:

  • objective(o::O, z): value of the objective at z (forward problem only). Return NaN or Inf if the value cannot be computed (for example, the forward problem did not converge); the optimisers treat it as a failed trial.
  • gradient!(dF, o::O, z): writes the derivative ∂F/∂z (a dual vector, no metric applied) into dF. The optimisers only call it for the z of their last call to objective on this oracle, so an implementation can reuse the forward state of that call and only pay for the adjoint.
  • bounds(o::O): (lb, ub), the bounds of z (scalars or vectors of the length of z), with lb < ub.
  • linear_constraint(o::O): (a, V) for the constraint aᵀz ≤ V (a ≥ 0 is a dual vector, for example the derivative of the volume), or nothing if there is none.

Methods with a default (Euclidean metric); they are not exported, extend them as Optimizers.inner:

  • inner(o::O, x, y): inner product of two primal vectors; default dot(x, y).
  • riesz!(g, o::O, dF): primal representative g = M⁻¹ dF of a dual vector; default copyto!(g, dF).

Optimisers only use these functions, broadcasting and global reductions (dot, maximum) on the vectors. If the bounds, the constraint or the objective change (continuation), call reset! on the optimiser.

source
HyperShape.Optimizers.FunctionOracle — Type
FunctionOracle(f, df!; lb = 0.0, ub = 1.0, constraint = nothing, metric = nothing)

Oracle built from plain functions, for analytical tests and small problems.

  • f(z): objective value.
  • df!(dF, z): writes ∂F/∂z into dF.
  • constraint = (a, V): linear constraint aᵀz ≤ V.
  • metric = m: diagonal metric, inner(x, y) = Σ mᵢ xᵢ yᵢ and riesz!(g, dF) = dF ./ m (cell volumes for P0 designs, lumped mass for P1 designs). nothing is the Euclidean metric.

evaluations(o) returns (value, derivative), the number of calls of each kind.

HyperShape.Optimizers.OC — Type
OC(; move = 0.2, damping = 0.5, bisection_tol = 1e-3, max_bisections = 200)

Optimality criteria update of Andreassen et al. (top88, 2011) for one linear constraint aᵀz ≤ V:

zᵢ ← clamp(zᵢ Bᵢ^damping, max(lbᵢ, zᵢ - m), min(ubᵢ, zᵢ + m)),   Bᵢ = max(0, -∂F/∂zᵢ) / (λ aᵢ),

with m = move * (ub - lb) and λ > 0 found by bisection on aᵀz = V, starting from [0, 1e9]. The bisection stops when (λ₂ - λ₁)/(λ₁ + λ₂) ≤ bisection_tol and, as in top88, keeps the design of the last midpoint, so the constraint holds up to the bisection tolerance. With the defaults, the step is the one of top88.

Requires a linear constraint with a > 0. The objective is evaluated once per step and the new design is not evaluated (f_new = NaN, kkt = NaN). If the move limit does not allow reaching aᵀz ≤ V (infeasible start), the step is still taken and violation > 0 in the StepInfo.

HyperShape.Optimizers.SiMPL — Type
SiMPL(; linesearch = :armijo, c1 = 1e-4, max_backtracks = 30, max_growth = 10.0, root_tol = 1e-12,
        max_root_iterations = 100)

Sigmoidal mirror descent with a projected latent variable (Keith, Kim, Lazarov and Surowiec, arXiv:2409.19341; Kim, Lazarov, Surowiec and Keith, arXiv:2411.19421).

The design is written as z = lb + (ub - lb) σ(ψ) with the sigmoid σ(x) = 1/(1 + e⁻ˣ), so every iterate satisfies the bounds strictly. One step, with g = M⁻¹ ∂F/∂z (see riesz!):

ψ ← ψ - α (g + μ M⁻¹a),

where μ ≥ 0 is zero if the constraint aᵀz ≤ V is inactive and otherwise solves aᵀz(ψ) = V (Newton iteration kept inside a bracket).

Step size: α₀ = 1/maximum(abs, g) after init/reset!; afterwards √(α_GBB α_prev) with the generalised Barzilai–Borwein step α_GBB = (ψₖ - ψₖ₋₁, zₖ - zₖ₋₁)_M / |(gₖ - gₖ₋₁, zₖ - zₖ₋₁)_M|, capped at max_growth * α_prev (each rejected trial costs a forward solve). The step is halved until

  • linesearch = :armijo: F(z_new) ≤ F(z) + c1 ∂F/∂z ⋅ (z_new - z), or
  • linesearch = :bregman: F(z_new) ≤ F(z) + ∂F/∂z ⋅ (z_new - z) + D(z_new, z)/α, with D the Bregman divergence of the (scaled) Fermi–Dirac entropy in the metric M.

A trial with a non-finite objective counts as failed. If no step is accepted after max_backtracks halvings, z is left unchanged and accepted = false. The tests allow a decrease lost in rounding (10 eps |F|), so a converged design keeps returning accepted steps with a negligible change instead of a failed line search.

Cost per step: one call to gradient! and one call to objective per trial (the value at the accepted trial is reused as the value of the next step). After init, reset! or a change of z by the caller, one more objective.

Optimality measure (kkt in StepInfo): (1, η)_M with λ = (ψ_trial - ψ)/α at the first trial of the step and η = max(-(z - lb) λ, (ub - z) λ) (eq. 23a of arXiv:2411.19421).

Requires a ≥ 0 (not all zero) in the linear constraint.

HyperShape.Optimizers.StepInfo — Type
StepInfo

What step! reports about one design step.

  • accepted: false if no acceptable step was found; z is then left unchanged.
  • f: objective at the design before the step.
  • f_new: objective at the new design, if the optimiser evaluated it (NaN otherwise).
  • kkt: optimality measure at the design before the step, if the optimiser computes one (NaN otherwise).
  • change: maximum(abs, z_new - z_old).
  • step: step size (SiMPL) or move limit (OC) used.
  • violation: max(0, aᵀz - V) of the linear constraint at the returned design (0 without constraint).
  • evaluations: number of calls to objective in the step (forward solves).
  • multiplier: multiplier of the linear constraint used in the step: in OC the λ of the last bisection (never 0), in SiMPL the shift μ of the volume projection (0 if the constraint is inactive); NaN without a constraint or when the step fails.

HyperShape.Optimizers.shrink! — Function
shrink!(opt::Optimizer, state, factor)

Called by the loop after it rejected the last step and restored z to its value before that step. Rolls back the memory of the optimiser to the start of that step and multiplies the size of the next step (or the move limit) by factor (0 < factor < 1). Consecutive calls accumulate; the reduction is dropped once a step stands (the next step! is called without a shrink! in between) or after reset!.

HyperShape.Operators — Module
HyperShape.Operators

Operators over HyperFEM computational models.

  • LinearOperator: auxiliary linear solves (filter, reaction–diffusion step, velocity extension). The model carries the bilinear form only and HyperShape supplies the right-hand side.
  • StateOperator: forward and adjoint states. The model carries the user's full weak forms.

Both declare their dependencies explicitly (depends = ...): objects with a version counter.

source
HyperShape.Operators.AbstractOperator — Type
AbstractOperator

Common supertype of LinearOperator and StateOperator.

source
HyperShape.Operators.LinearOperator — Type
LinearOperator(model; depends, solve)

Linear solve with a matrix built by a HyperFEM model (typically a StaticLinearModel with the bilinear form alone) and a right-hand side supplied by HyperShape.

  • model: the computational model; its matrix and solver are the user's.
  • depends: the objects the matrix depends on (one object or a tuple; each implements version); () if the matrix never changes. Mandatory.
  • solve: user function (model, b, ctx, stale) -> x that solves with the right-hand side b and returns the solution vector. stale is true when something in depends changed since the last solve, so the user can re-assemble, for example solve = (m, b, ctx, stale) -> solve!(m, b; Assembly = stale). Mandatory.

The matrix must be the one the model assembled at construction (no dependency has changed yet). The returned vector is copied, so it may be a buffer of the model. invalidate! makes the next solve stale whatever the dependencies (the consistency checks use it).

source
HyperShape.Operators.OptContext — Type
OptContext(phase::Symbol = :setup)

Context of the optimisation, passed to every solve function of the user (solve = (m, ctx) -> …) and to the post-processing. Read-only for the user; HyperShape updates it. Fields:

  • iteration: design iteration (0 before the loop starts).
  • attempt: attempt of the current iteration (1, or more after rejected steps).
  • trial: number of forward evaluations requested in the current iteration.
  • phase: :setup (constructors), :check (check_consistency), :optimization (the current design of the loop and its adjoint) or :linesearch (a trial design requested by the optimiser; with SiMPL the design that is finally accepted is first solved in this phase).
  • continuation: named tuple with the current values of the continued parameters, for example (β = 4.0,).

For example, RestartState = ctx.trial > 1 restarts a nonlinear solve from scratch at every evaluation after the first one of an iteration (a design tried after a rejected step, or a line-search trial).

source
HyperShape.Operators.StateOperator — Type
StateOperator(model; depends, solve)

Forward or adjoint state: a HyperFEM computational model built by the user (weak forms and solver are the user's) that is solved again only when one of its dependencies changed.

  • depends: the objects the state depends on (one object or a tuple), typically θ for a forward state and (θ, S) for its adjoint. Each implements version; physical fields and other state operators are brought up to date first. Mandatory.
  • solve: user function (model, ctx) -> result that solves the model, for example (m, ctx) -> solve!(m; stepping = …) or (m, ctx) -> solve!(m; Assembly = true). The result is either the solution vector (taken as converged) or a tuple whose last element is the convergence flag: a Bool, or 1/0 as the flagconv of (x, flagconv) returned by HyperFEM's nonlinear models. Mandatory.

get_state(S) is the state field of the model, created once, so the forms of other models (the adjoint) can capture it; it always holds the model's current solution vector.

Failures do not throw. When the solve does not converge, or a state this one depends on did not converge (then this one is not solved), apply! returns false, is_converged is false and the functionals that need the state return NaN. After a failure get_state(S) holds whatever the model left (for HyperFEM's nonlinear models, the last converged load increment), not a solution. A failed solve is not repeated until a dependency changes; the next solve starts from what the model holds, as decided by the user's solve (RestartState in HyperFEM).

source

HyperShape.Variables — Module
HyperShape.Variables

Design variables at three linked levels:

LevelObjectWhat it is
zOptVariableswhat the optimiser sees: one vector made of blocks, with bounds
xDesignFieldsdesign fields on the design mesh (cell-wise P0 or nodal P1)
θPhysicalFieldsphysical fields read by the weak forms at the quadrature points

Each level is built from the previous one, and only HyperShape writes them (in place). The maps x → θ (HelmholtzFilter, Heaviside, Identity) are composed with ∘ in the mathematical order: Heaviside(β = 1.0, η = 0.5) ∘ HelmholtzFilter(Sf; measure = dΩ) filters first and projects after.

Sensitivities travel backwards with design_gradient!: a linear form in δθ for each physical field gives the derivative with respect to z.

The vectors HyperShape assembles (load vector of a filter, sensitivities) use backend = :compiled by default (HyperFEMKernels: forms compiled once into threaded kernels) or backend = :lazy (Gridap's assembler); see HelmholtzFilter and PhysicalFields. Both give the same vectors up to rounding. The compiled backend is faster from tens of thousands of cells on, already with one thread, and scales with the threads (julia -t N); on meshes of about a thousand cells both take well under a millisecond per vector.

HyperShape.Variables.FieldMap — Type
FieldMap

Supertype of the maps x → θ. Compose them with ∘ in the mathematical order: (g ∘ f)(x) = g(f(x)).

source
HyperShape.Variables.FieldVariable — Type
FieldVariable(V; bounds, init)

Block of OptVariables holding the free values of a scalar design field in the space V (cell-wise P0 or nodal P1 Lagrangian, without Dirichlet conditions; the bounds act on the free values, which bound the field only for these two spaces). bounds = (lb, ub) with lb < ub; init is a number or a vector of the length of the free values, inside the bounds. Both are mandatory.

source
HyperShape.Variables.Heaviside — Type
Heaviside(; β, η)

Smooth Heaviside projection (Wang, Lazarov and Sigmund, 2011), applied point by point at the quadrature points:

H(ρ) = (tanh(βη) + tanh(β(ρ - η))) / (tanh(βη) + tanh(β(1 - η)))

β > 0 (sharpness) and 0 < η < 1 (threshold) are mandatory. β can be changed during the optimisation with set_beta! (continuation); every field and form built from this object sees the new value, and the physical fields that use it count as changed.

source
HyperShape.Variables.HelmholtzFilter — Type
HelmholtzFilter(op::LinearOperator; measure, backend = :compiled)

PDE filter (Lazarov and Sigmund, 2011): the filtered field ρ̃ solves a(ρ̃, v) = ∫(x v) dΩ for all v, where a is the bilinear form of the model of op (for example a(ρ̃, v) = ∫(r^2 ∇(ρ̃)⋅∇(v) + ρ̃ v)dΩ, solver chosen by the user) and dΩ = measure. The output is a field of the trial space of that model (usually P1), also for a P0 design field. The bilinear form must be symmetric (the same solve gives the transpose for the sensitivities; this is not checked) and the trial space may only have homogeneous Dirichlet values (checked).

backend selects who assembles the load vectors of the filter: :compiled (default, HyperFEMKernels) or :lazy (Gridap). It is independent of the backend of the filter model, which assembles the matrix.

Cost: one assembly of a load vector and one solve each time the design changes, and the same for each sensitivity pulled back.

HyperShape.Variables.PhysicalFields — Type
PhysicalFields(x::DesignFields; name = map, other = :source => map, ..., backend = :compiled)

Physical fields θ, the ones the weak forms read. Each one comes from one design field through a map (a FieldMap, possibly composed with ∘): ρ = map uses the design field ρ; E = :ρ => map uses the design field ρ under another name, so several physical fields can come from the same design field (their sensitivities are added). Every design field must be used. The constructor brings the fields up to date once, calling the solve functions of the operators with ctx = OptContext(:setup). Read a field as θ.ρ: a fixed object (an FEFunction or a CellField) updated in place, so the weak forms can capture it.

backend (a reserved name: no physical field can be called backend) selects who assembles the sensitivities on the design spaces: :compiled (default, HyperFEMKernels) or :lazy (Gridap).

HyperShape.Variables.design_gradient! — Method
design_gradient!(gz, θ::PhysicalFields, forms::NamedTuple, ctx; key = 0) -> gz

Derivative with respect to z of a quantity whose derivative with respect to the physical fields is given as linear forms: forms = (ρ = δ -> ∫(… * δ)dΩ, …), one entry per physical field it depends on (missing fields contribute nothing). The forms are pulled back through the maps x → θ (transposed filters, derivatives of the projections), assembled on the design spaces, added over the physical fields that share a design field, and mapped to z. Writes gz (a vector of the length of z).

key identifies the quantity for the compiled backend, which keeps the compiled forms of the last keys used: with a different key for each quantity (objective, each constraint) the forms are only rebound at every call; forms of different structure under one key are correct too, their kernels are compiled again at each call (a few milliseconds). Avoid creating the Measure inside a form or capturing a new FEFunction at every call: both change the structure of the form.

source
HyperShape.Functionals.Functional — Type
Functional(Jform, DJform, S, A, θ; scale)
Functional(Jform, DJform, θ; scale)

Objective or constraint.

With states (first form):

  • Jform(u, θ): value, a DomainContribution (∫(…)dΩ) or a number; u = get_state(S).
  • DJform(u, p, θ): total derivative with respect to the physical fields, ∂J/∂θ − ∂R/∂θ contracted with the adjoint p = get_state(A): a function δ -> ∫(… * δ)dΩ when θ has one field, or a named tuple of such functions ((ρ = δ -> …, E = δ -> …)), one per physical field it depends on.
  • S: forward StateOperator; A: adjoint state operator, which solves a(w, p) = ∂J/∂u[w] for all w (with a the tangent of the forward problem) on a space with homogeneous Dirichlet values; S must depend on θ and A on θ and S. For a self-adjoint functional pass A = S (then p = u; valid only when the Dirichlet values of the state are zero) and include the sign in DJform. Non-zero Dirichlet values in the trial space of the adjoint are detected when the gradient is computed.

Design only (second form, volume, perimeter): Jform(θ) and DJform(θ).

scale is mandatory: a positive number, :initial (the absolute value of the first finite evaluation; an error if it is zero) or 1.0 for no scaling. The value and the derivative are divided by it.

The value is kept until θ or a state changes; the gradient is assembled at every call (one adjoint solve only when the design changed, one transposed filter solve per filter and one assembly per call).

If a state does not converge, functional_value returns NaN and functional_gradient! fills the gradient with NaN (the optimisers treat it as a failed trial).

HyperShape.Checks.check_consistency — Method
check_consistency(J1, J2, …; ctx = OptContext(:check), kwargs...) -> ConsistencyReport
check_consistency((name1 = J1, name2 = J2, …); ctx = OptContext(:check), kwargs...)

Checks, at the current design, that the derivatives the user wrote and the dependencies the user declared are consistent. The functionals must share the same optimisation variables z. Four kinds of checks:

  1. Gradient of each functional (Taylor test): J(z + hδ) − J(z) − h⟨∇J, δ⟩ must decrease with order 2 when h is halved. It covers DJform, the adjoint state and the maps x → θ at once.
  2. Design chain of each physical field (Taylor test of ½∫θ² through the maps alone, for every PhysicalFields reached from the functionals): if it passes and the gradient of a functional fails, the error is in DJform or in the adjoint, not in the maps.
  3. Symmetry of each filter: cᵀA⁻¹b = bᵀA⁻¹c for two random vectors, with the user's solve.
  4. Dependencies: at a perturbed design, value and gradient computed as usual are compared with the ones obtained after forcing every state and filter reached through the declared dependencies to assemble and solve again. A difference means that one of those operators depends on something it does not declare (for example a filter matrix that reads the design with depends = (), or a state listed in depends that under-declares its own dependencies). An object that no declared dependency leads to cannot be checked: its stale values go unnoticed when DJform treats it as fixed too.

Optionally, tangents = (S => (res, jac), …) adds a Taylor test of the tangent jac(u, du, v) against the residual res(u, v) of the state S at its current solution, in a random direction of its free values (the user's forms in Gridap's convention; for HyperFEM's load-factor forms pass res(Λ), jac(Λ)).

A Taylor test passes when two consecutive steps give an observed order of at least min_rate (both errors above rounding), or when every error is at rounding level while J does change along δ (a functional linear in z). It fails, as not tested, when J does not change along δ at all (for example a fully saturated projection): choose another direction or design. It fails as inconclusive when only the largest step gives an error above rounding (a nearly linear functional): try a larger h0. With h0 = 1e-2 a relative error of about 0.1 % in a gradient can still pass.

Keyword arguments:

  • ctx: passed to the solve functions (default OptContext(:check)).
  • direction: direction δ in z (default: random, scaled by the width of the bounds, zero within 1e-3 of the width from a bound).
  • h0: first step (default: 90 % of the largest step that keeps z + hδ inside the bounds, at most 1e-2).
  • steps = 5: number of steps of each Taylor test (h halved each time).
  • seed = 1: seed of the random directions and vectors.
  • min_rate = 1.8: observed order required.
  • rtol = 1e-8: relative tolerance of the symmetry and dependency checks (increase it with iterative solvers or Newton tolerances).

Cost: each forward state is solved at most steps + 4 times and each adjoint state at most 4 times (states shared by several functionals are solved once per design); each filter is solved once per step for checks 1 and 2, twice for check 3, and again whenever a gradient is pulled back. Use small meshes for nonlinear problems.

On return, z holds its initial values and the fields and states are brought back to it (one more solve of each state). The scales of the functionals are the ones they had; a scale = :initial not yet fixed stays unfixed (its functional is checked unscaled), fixed scales are used as they are. If a dependency check fails, the operators may hold matrices assembled during the check: fix the depends and build them again. Errors thrown by the user's forms or solves propagate (z and the scales are restored first).

HyperShape.Methods — Module
HyperShape.Methods

Optimisation problems and methods. A method is an operator z ↦ z⁺ over the functionals; all methods share one loop (evaluate, differentiate, step, accept or reject, continuation, stopping, checkpoint) and only the step is specific:

  • SIMP: density methods; the step is any Optimizer of HyperShape.Optimizers (OC, SiMPL).

Reaction–diffusion and level-set methods (phase 2) will plug into the same loop.

HyperShape.Methods.Checkpoint — Type
Checkpoint(path; every)

Writes the state of the optimisation to the folder path every every accepted iterations, and also when the optimisation stops or fails: checkpoint.toml (iteration, continuation stage, scales of the functionals, sizes and the names of the other two files), z_<iteration>.bin (the design, raw Float64) and history_<iteration>.csv. The design and the history are written first and checkpoint.toml last, under a temporary name and then renamed, so the three files always belong to the same iteration; older files are then deleted. Resume with solve!(…; resume = load_checkpoint(path)).

HyperShape.Methods.Continuation — Type
Continuation(; every, name = object => values, …)

Continuation of parameters in stages: Continuation(β = H => [1, 2, 4, 8, 16, 32]; every = 40) uses β = 1 in the first stage, 2 in the second, and so on. A stage ends after every iterations, or earlier when the StopCriteria are met; the optimisation can only stop in the last stage. At each jump the memory of the optimiser is forgotten (reset!), which costs one more forward solve. All value lists have the same length (the number of stages). Supported objects: Heaviside (β, through set_beta!).

Euclidean()

HyperShape.Methods.FunctionalOracle — Type
FunctionalOracle

Oracle (see HyperShape.Optimizers.AbstractOracle) of an Optimization: objective and gradient! call the objective functional at the requested design, linear_constraint gives (a, V) computed once at the start, and inner/riesz! use the metric of the method.

  • It is the only writer of the variables z; a design equal to the current one is not set again, so the value cache of the functional avoids repeated forward solves.
  • It keeps a copy of the design, value and derivative of its last gradient!: after a rejected step, the optimiser asks again at that design and gets them without solves.
  • A gradient that is not finite throws OptimizationFailure.

LumpedMass(dΩ)

Diagonal metric m = ∫ v dΩ assembled on each design space: the cell volumes for a P0 design, the lumped mass (row sums of the mass matrix) for a P1 design. inner(x, y) = Σ mᵢ xᵢ yᵢ, riesz!(g, dF) = dF ./ m.

OptHistory

HyperShape.Methods.OptResult — Type
OptResult

Result of solve!: status (:converged, :maxiter or :stalled, the last when the optimiser found no acceptable step in the last continuation stage; in an earlier stage this ends the stage), reason (the criterion met, or nothing), iterations, objective (scaled, at the final design), history (OptHistory), state (the optimiser state) and start_scaling (the factor t by which an infeasible starting design was scaled towards the lower bound, nothing if it was not). HyperShape.Methods.Optimization — Type
Optimization(z; objective, linear_constraints = ())

Optimisation problem over the variables z: minimise the Functional objective subject to the bounds of z and, in phase 0, at most one linear constraint g(z) ≤ 0, given as a design-only functional (for example the volume of an unprojected density, Functional(θ -> sum(∫(θ.ρ)dΩ) - Vmax, θ -> (δ -> ∫(δ)dΩ), θv; scale = Vmax) with θv = PhysicalFields(x; ρ = Identity())). Its linearity in z is checked when the optimisation starts. Nonlinear constraints (constraints = …) come in phase 1.

Volume and projection

A linear constraint acts on the design, not on the physical density. The Helmholtz filter preserves the volume, but a Heaviside projection does not: with projection the physical volume can differ markedly from the constrained one (half MBB beam, 150×50, target 0.5: the projected density ends at 0.64–0.68). Constraining the physical volume needs a nonlinear constraint, planned for the next step.

The problem owns the context ctx (OptContext) that reaches the solve functions of the user.

HyperShape.Methods.OptimizationFailure — Type
OptimizationFailure(msg)

Thrown by solve! when the optimisation cannot continue: the forward problem does not converge at the current design (first iteration or right after a continuation jump), every attempt of a step was rejected, or a gradient is not finite (failed adjoint). z, the fields and the states are left at the last accepted design, and the checkpoint (if any) is written first. history holds the OptHistory up to the last accepted iteration and iterations its number (nothing and 0 when thrown outside the loop).

source
HyperShape.Methods.RejectStep — Type
RejectStep(; shrink, max)

What to do when the forward problem does not converge at the design proposed by the optimiser: go back to the previous design, call shrink! on the optimiser with shrink (0 < shrink < 1: OC multiplies its move limit) and try again, at most max attempts per iteration; then throw OptimizationFailure. Both are mandatory.

Optimisers that evaluate their trials (SiMPL) handle failures inside their line search, so for them this only applies if a step is accepted at a design that cannot be evaluated again.

HyperShape.Methods.SIMP — Type
SIMP(optimizer; metric)

Density method: the step is optimizer (any Optimizer: OC(…), SiMPL(…)). metric is mandatory: LumpedMass(dΩ) or Euclidean(), or a named tuple with one of them per block of z. OC ignores it; SiMPL uses it in its step and its optimality measure.

HyperShape.Methods.StopCriteria — Type
StopCriteria(; change = nothing, kkt = nothing, objective = nothing, window = nothing)

Convergence criteria; each one is off unless given, and the first one met stops the optimisation (in the last stage of the continuation). change: maximum(abs, Δz) of the step below this value. kkt: optimality measure of the optimiser below this value (SiMPL; an optimiser that does not compute it, such as OC, gives an error). objective: relative change of the objective over the last window iterations (mandatory with objective) below this value, counting only iterations of the current continuation stage.

Gridap.Algebra.solve! — Method
solve!(problem::Optimization, method::SIMP; maxiter, on_failure, stop = nothing, schedule = nothing,
       checkpoint = nothing, post = nothing, resume = nothing, verbose = 2, io = stdout) -> OptResult

Runs the optimisation from the current values of z. Mandatory: maxiter (total iterations, resumed ones included) and on_failure (RejectStep). Optional: stop (StopCriteria; without it the loop runs maxiter iterations), schedule (Continuation), checkpoint (Checkpoint), post (a function post(ctx) called after each accepted iteration, with the fields and the forward state at the accepted design; the adjoint state is still the one of the previous design) and resume (the result of load_checkpoint), verbose and io.

Screen output (verbose, default 2, printed to io): 0 nothing; 1 a banner (variables, constraint, metric, continuation, stopping criteria), the events (continuation jumps, rejected steps, stalls, a scaled start), a closing ✓/⚠/✗ line and a summary of solves and time; 2 also a row per iteration: objective, its relative change, constraint (red above 1e-3), optimality measure, change of z, step, multiplier, continued parameters, forward, adjoint and filter solves, and time. true is 2, false is 0. The summary counts every solve of the call (those of rejected or stalled trials, the setup and the final synchronisation included).

If the starting design (not a resumed one) violates the linear constraint, it is scaled towards the lower bound, z = lb + t (z − lb) on the entries the constraint acts on, so that it holds with equality; t is returned in result.start_scaling and reported as an event when verbose ≥ 1.

Each iteration: the optimiser takes a step from the current design; the loop evaluates the new design (no solve when the optimiser already did, as SiMPL); if the forward problem does not converge there, the design is restored, the step shrunk and tried again. Solves per iteration: OC one filter, one forward, one adjoint (none for a self-adjoint functional) and one transposed filter; SiMPL one filter and one forward per trial of its line search (usually one), one adjoint and one transposed filter; one more forward after each continuation jump. The linear constraint costs nothing in the loop (its vector is computed once at the start).

load_checkpoint(path) -> NamedTuple
