HyperShape.Optimizers — Module
HyperShape.Optimizers

Optimisers for problems with a box-bounded design vector z and at most one constraint g(z) ≤ 0, linear or not (for example the volume of a projected density).

The module is independent of finite elements: an optimiser sees vectors, bounds and an oracle (see AbstractOracle). A new optimiser is a subtype of Optimizer that implements the four functions of the contract:

state = init(opt, z, oracle)            # memory and history
info  = step!(opt, state, z, oracle, ctx) # overwrites z with the next design, returns a StepInfo
reset!(opt, state)                      # forget the history (continuation jump, remeshing)
shrink!(opt, state, factor)             # roll back the last step and reduce the next one

HyperShape.Optimizers.AbstractOracle — Type
AbstractOracle

What an optimiser may ask about the problem. Methods to implement for a subtype O:

  • objective(o::O, z): value of the objective at z (forward problem only). Return NaN or Inf if the value cannot be computed (for example, the forward problem did not converge); the optimisers treat it as a failed trial.
  • gradient!(dF, o::O, z): writes the derivative ∂F/∂z (a dual vector, no metric applied) into dF. The optimisers only call it for the z of their last call to objective on this oracle, so an implementation can reuse the forward state of that call and only pay for the adjoint.
  • bounds(o::O): (lb, ub), the bounds of z (scalars or vectors of the length of z), with lb < ub.
  • The constraint g(z) ≤ 0, if there is one (at most one), in either of two ways:
    • linear: linear_constraint(o::O) returns (a, V) for aᵀz ≤ V (a ≥ 0 is a dual vector, for example the derivative of the volume); the optimisers then use a and V exactly;
    • nonlinear: linear_constraint(o::O) returns nothing and the oracle implements has_constraint(o::O) = true, constraint(o::O, z) (the value of g, scaled, ≤ 0 when feasible; NaN or Inf if it cannot be computed) and constraint_gradient!(dG, o::O, z) (∂g/∂z at the z of the last call to constraint).
    For a linear constraint the last three have defaults built from (a, V).

Methods with a default (Euclidean metric); they are not exported, extend them as Optimizers.inner:

  • inner(o::O, x, y): inner product of two primal vectors; default dot(x, y).
  • riesz!(g, o::O, dF): primal representative g = M⁻¹ dF of a dual vector; default copyto!(g, dF).

Optimisers only use these functions, broadcasting and global reductions (dot, maximum) on the vectors. If the bounds, the constraint or the objective change (continuation), call reset! on the optimiser.

HyperShape.Optimizers.FunctionOracle — Type
FunctionOracle(f, df!; lb = 0.0, ub = 1.0, constraint = nothing, metric = nothing)

Oracle built from plain functions, for analytical tests and small problems.

  • f(z): objective value.
  • df!(dF, z): writes ∂F/∂z into dF.
  • constraint = (a, V) with a vector a: linear constraint aᵀz ≤ V.
  • constraint = (g, dg!) with functions: nonlinear constraint g(z) ≤ 0, dg!(dG, z) writes ∂g/∂z.
  • metric = m: diagonal metric, inner(x, y) = Σ mᵢ xᵢ yᵢ and riesz!(g, dF) = dF ./ m (cell volumes for P0 designs, lumped mass for P1 designs). nothing is the Euclidean metric.

evaluations(o) returns (value, derivative), the number of calls of each kind.

HyperShape.Optimizers.OC — Type
OC(; move = 0.2, damping = 0.5, bisection_tol = 1e-3, max_bisections = 200, constraint_tol = 1e-4,
     max_corrections = 8, adapt = (0.7, 1.2), move_min = 1e-3)

Optimality criteria update of Andreassen et al. (top88, 2011) for one constraint g(z) ≤ 0:

zᵢ ← clamp(zᵢ Bᵢ^damping, max(lbᵢ, zᵢ - m), min(ubᵢ, zᵢ + m)),   Bᵢ = max(0, -∂F/∂zᵢ) / (λ aᵢ),

with m = move * (ub - lb) and λ > 0 found by bisection on aᵀz = V, starting from [0, 1e9].

  • Linear constraint aᵀz ≤ V: the bisection stops when (λ₂ - λ₁)/(λ₁ + λ₂) ≤ bisection_tol and, as in top88, keeps the design of the last midpoint, so the constraint holds up to the bisection tolerance. With adapt = nothing the step is the one of top88. Requires a > 0.
  • Nonlinear constraint (for example the volume of a projected density): a = ∂g/∂z at the current design (floored at 1e-12 maximum(a), since a filter can leave tiny or negative entries where a projection saturates; an entry with a zero derivative moves up to the move limit in the direction of descent) and the linearised constraint aᵀz ≤ aᵀzₖ - g(zₖ) - s. The shift s is then corrected (chord, then bounded secant steps, at most max_corrections) until |g(z_new)| ≤ constraint_tol, evaluating the true g once per correction; s is kept for the next step (reset! clears it). The bisection is solved to min(bisection_tol, 1e-7) so that the corrections see a smooth function. If the move limit does not allow meeting the constraint, the step is still taken.

Move limits. With adapt = (dec, inc) (default) each entry has its own move limit mᵢ: multiplied by dec when its last step changed sign with respect to the one before, by inc when it kept it, and kept in [move_min, move] (as the move limits of MMA, Svanberg 1987). It damps the oscillation of OC at the interface when a tanh projection is sharp (a step of move is wider than the projection band, about 1/β). reset! (a continuation jump) restores every mᵢ to move; shrink! scales them all, and the retry after a rejected step does not update them. adapt = nothing gives the scalar move limit of top88. move can follow a continuation, Continuation(β = H => […], move = oc => […]) (see set_move!); with adapt it is the ceiling of the limits. The step of the StepInfo is the mean of the limits over all entries (those at a bound included).

The objective is evaluated once per step and the new design is not evaluated (f_new = NaN, kkt = NaN). If the move limit does not allow meeting the constraint (infeasible start), the step is still taken and violation > 0 in the StepInfo.

It also reports the stationarity measure of the design before the step (stationarity!, with the metric of the oracle, which the step does not use).

HyperShape.Optimizers.SiMPL — Type
SiMPL(; linesearch = :armijo, c1 = 1e-4, max_backtracks = 30, max_growth = 10.0, root_tol = 1e-12,
        max_root_iterations = 100, constraint_tol = 1e-6, max_corrections = 8)

Sigmoidal mirror descent with a projected latent variable (Keith, Kim, Lazarov and Surowiec, arXiv:2409.19341; Kim, Lazarov, Surowiec and Keith, arXiv:2411.19421).

The design is written as z = lb + (ub - lb) σ(ψ) with the sigmoid σ(x) = 1/(1 + e⁻ˣ), so every iterate satisfies the bounds strictly. One step, with g = M⁻¹ ∂F/∂z (see riesz!):

ψ ← ψ - α (g + μ M⁻¹a),

where μ ≥ 0 is zero if the constraint aᵀz ≤ V is inactive and otherwise solves aᵀz(ψ) = V (Newton iteration kept inside a bracket).

Step size: α₀ = 1/maximum(abs, g) after init/reset!; afterwards √(α_GBB α_prev) with the generalised Barzilai–Borwein step α_GBB = (ψₖ - ψₖ₋₁, zₖ - zₖ₋₁)_M / |(gₖ - gₖ₋₁, zₖ - zₖ₋₁)_M|, capped at max_growth * α_prev (each rejected trial costs a forward solve). The step is halved until

  • linesearch = :armijo: F(z_new) ≤ F(z) + c1 ∂F/∂z ⋅ (z_new - z), or
  • linesearch = :bregman: F(z_new) ≤ F(z) + ∂F/∂z ⋅ (z_new - z) + D(z_new, z)/α, with D the Bregman divergence of the (scaled) Fermi–Dirac entropy in the metric M.

A trial with a non-finite objective counts as failed. If no step is accepted after max_backtracks halvings, z is left unchanged and accepted = false. The tests allow a decrease lost in rounding (10 eps |F|), so a converged design keeps returning accepted steps with a negligible change instead of a failed line search.

Cost per step: one call to gradient! and one call to objective per trial (the value at the accepted trial is reused as the value of the next step). After init, reset! or a change of z by the caller, one more objective.

Optimality measure (kkt in StepInfo): (1, η)_M with λ = (ψ_trial - ψ)/α at the first trial of the step and η = max(-(z - lb) λ, (ub - z) λ) (eq. 23a of arXiv:2411.19421).

Requires a ≥ 0 (not all zero) in the linear constraint.

Nonlinear constraint g(z) ≤ 0 (for example the volume of a projected density; an extension of the method, which the references only state for a linear volume): at each step a = ∂g/∂z at the current design (floored at 1e-12 maximum(a)) and the linearised constraint aᵀz ≤ aᵀzₖ - g(zₖ) - s takes the place of aᵀz ≤ V. For each trial, the shift s is corrected (chord, then bounded secant steps, at most max_corrections, one evaluation of the true g each) until -constraint_tol ≤ g(z_trial) ≤ 0, aiming at -constraint_tol/2, so every accepted iterate is feasible; s is kept between steps (reset! clears it) and divided by 4 each time the line search halves the step (the linearisation error falls with the square of the step). A tolerance much larger than 1e-6 can stall the line search, because the slack of the constraint then moves the objective more than the expected decrease. At an infeasible design (g > constraint_tol: a start or a continuation jump) the step restores feasibility: the first trial with a finite objective is accepted, without the Armijo test.

It also reports the stationarity measure of the design before the step (stationarity!), the criterion of the paper.

HyperShape.Optimizers.StepInfo — Type
StepInfo

What step! reports about one design step.

  • accepted: false if no acceptable step was found; z is then left unchanged.
  • f: objective at the design before the step.
  • f_new: objective at the new design, if the optimiser evaluated it (NaN otherwise).
  • kkt: optimality measure at the design before the step, if the optimiser computes one (NaN otherwise).
  • change: maximum(abs, z_new - z_old).
  • step: step size (SiMPL) or move limit (OC) used; with adaptive move limits, their mean over all entries.
  • violation: max(0, g(z)) of the constraint at the returned design (0 without constraint).
  • evaluations: number of calls to objective in the step (forward solves).
  • multiplier: multiplier of the constraint (linearised at the current design if it is nonlinear) used in the step: in OC the λ of the last bisection (never 0), in SiMPL the shift μ of the volume projection (0 if the constraint is inactive); NaN without a constraint or when the step fails.
  • stationarity: stationarity measure at the design before the step, S = ‖z − P(z − g)‖_M (see stationarity!); NaN if the optimiser does not compute it.

HyperShape.Optimizers.shrink! — Function
shrink!(opt::Optimizer, state, factor)

Called by the loop after it rejected the last step and restored z to its value before that step. Rolls back the memory of the optimiser to the start of that step and multiplies the size of the next step (or the move limit) by factor (0 < factor < 1). Consecutive calls accumulate; the reduction is dropped once a step stands (the next step! is called without a shrink! in between) or after reset!.

HyperShape.Optimizers.stationarity! — Method
stationarity!(w, oracle, z, g, ga, a, V) -> S

Stationarity measure of the paper of SiMPL (Kim, Lazarov, Surowiec, Keith, 2024): S = ‖z − P(z − g)‖_M, with g = M⁻¹ ∂F/∂z (see riesz!), M the metric of the oracle and P the projection, in that metric, onto the bounds and the constraint aᵀz ≤ V (a = nothing: bounds only; a nonlinear constraint is linearised at z). For a diagonal metric P(y) = clamp(y − c M⁻¹a, lb, ub) with the smallest c ≥ 0 that meets the constraint, found by bisection; ga = M⁻¹a (pass riesz!(ga, oracle, a), not a). w is a work vector. It is absolute: it depends on the scale of the objective and on the metric (with the Euclidean metric it depends on the mesh). Returns NaN when no point within the bounds meets the constraint (V below the minimum of aᵀz over the bounds) or when V is not finite. Only broadcasting and reductions: no allocations.

HyperShape.Operators — Module
HyperShape.Operators

Operators over HyperFEM computational models.

  • LinearOperator: auxiliary linear solves (filter, reaction–diffusion step, velocity extension). The model carries the bilinear form only and HyperShape supplies the right-hand side.
  • StateOperator: forward and adjoint states. The model carries the user's full weak forms.

Both declare their dependencies (objects with a state_version counter), positionally or with depends = .... For a StaticLinearModel both have a default solve (default_solve); any other model needs the user's. AdjointOperator builds the adjoint state of a forward one.

HyperShape.Operators.LinearOperator — Type
LinearOperator(model[, deps]; depends = (), solve = default_solve(LinearOperator, model))

Linear solve with a matrix built by a HyperFEM model (typically a StaticLinearModel with the bilinear form alone) and a right-hand side supplied by HyperShape.

  • model: the computational model; its matrix and solver are the user's.
  • deps or depends: the objects the matrix depends on (one object or a tuple; each implements state_version), given once. Default (): the matrix never changes. A dependency captured by the bilinear form and not declared gives stale results; check_consistency detects it.
  • solve: function (model, b, ctx, stale) -> x that solves with the right-hand side b and returns the solution vector. stale is true when something in the dependencies changed since the last solve, so it can re-assemble. Default for a StaticLinearModel: solve!(m, b; Assembly = stale) (default_solve); mandatory for any other model.

The matrix must be the one the model assembled at construction (no dependency has changed yet). The returned vector is copied, so it may be a buffer of the model. invalidate! makes the next solve stale whatever the dependencies (the consistency checks use it).

HyperShape.Operators.OptContext — Type
OptContext(phase::Symbol = :setup)

Context of the optimisation, passed to every solve function of the user (solve = (m, ctx) -> …) and to the post-processing. Read-only for the user; HyperShape updates it. Fields:

  • iteration: design iteration (0 before the loop starts).
  • attempt: attempt of the current iteration (1, or more after rejected steps).
  • trial: number of forward evaluations requested in the current iteration.
  • phase: :setup (constructors), :check (check_consistency), :optimization (the current design of the loop and its adjoint) or :linesearch (a trial design requested by the optimiser; with SiMPL the design that is finally accepted is first solved in this phase).
  • continuation: named tuple with the current values of the continued parameters, for example (β = 4.0,).

For example, RestartState = ctx.trial > 1 restarts a nonlinear solve from scratch at every evaluation after the first one of an iteration (a design tried after a rejected step, or a line-search trial).

HyperShape.Operators.Parameter — Type
Parameter(value)

A number of the user that may change during the optimisation: the penalty of a material interpolation, a load factor, a weight. p[] reads it and p[] = v changes it (its state_version grows only if the value changes). Read it inside the weak forms (E(ρ) = Emin + ρ^p[] * (1 - Emin)) and give it as a dependency of the operators whose models read it (StateOperator(model, (θ, p))), so they solve again when it changes; inside a map, give it in the parameters of a PointwiseMap. Continue it in stages with Continuation(p = p => [1, 2, 3]; every). A functional that reads it directly (not through a state or θ) lists it in its parameters. A parameter read by a model but not declared as a dependency is not detected by check_consistency: after it changes, the operator would keep its old solution.

HyperShape.Operators.StateOperator — Type
StateOperator(model, deps; solve = default_solve(StateOperator, model))
StateOperator(model; depends, solve = …)

Forward or adjoint state: a HyperFEM computational model built by the user (weak forms and solver are the user's) that is solved again only when one of its dependencies changed. For the adjoint of a forward state use AdjointOperator.

  • deps or depends (given once, mandatory): the objects the state depends on (one object or a tuple), typically θ for a forward state. Each implements state_version; physical fields and other state operators are brought up to date first.
  • solve: function (model, ctx) -> result that solves the model. The result is either the solution vector (taken as converged) or a tuple whose last element is the convergence flag: a Bool, or 1/0 as the flagconv of (x, flagconv) returned by HyperFEM's nonlinear models. Default for a StaticLinearModel: solve!(m; Assembly = true) (default_solve). Mandatory for any other model, for example (m, ctx) -> solve!(m; stepping = …, RestartState = false); return the tuple, so that a load ramp that does not reach its final factor counts as not converged (an adjoint built on the tangent at the final factor would be inconsistent otherwise).

get_state(S) is the state field of the model, created once, so the forms of other models (the adjoint) can capture it; it always holds the model's current solution vector.

Failures do not throw. When the solve does not converge, or a state this one depends on did not converge (then this one is not solved), apply! returns false, is_converged is false and the functionals that need the state return NaN. After a failure get_state(S) holds whatever the model left (for HyperFEM's nonlinear models, the last converged load increment), not a solution. A failed solve is not repeated until a dependency changes; the next solve starts from what the model holds, as decided by the user's solve (RestartState in HyperFEM).

HyperShape.Operators.AdjointOperator — Function
AdjointOperator(S::StateOperator, model[, deps]; depends = (), solve = default_solve(StateOperator, model))
    -> StateOperator

Adjoint state of the forward state S: a StateOperator over the user's model (weak forms and solver are the user's; typically the tangent of the forward problem with test and trial swapped, evaluated at get_state(S), and the right-hand side ∂J/∂u). Its dependencies are those of S, then S, then the extra ones given in deps or depends (once), without repetitions. The trial space of model must have homogeneous Dirichlet values (checked here for the HyperFEM models that expose their spaces). It is solved only after S converged.

One adjoint covers one forward state: if S depends on another state S0 (for example through a field computed by S0), the sensitivity through S0 needs its own adjoint and is not included in the gradient of a Functional built on S; check_consistency detects it. A warning is given when this adjoint is built.

HyperShape.Operators.default_solve — Function
default_solve(::Type{<:AbstractOperator}, model)

Solve function used when the user gives none. Only a HyperFEM StaticLinearModel has one, and it calls the model's own solver (HyperShape never chooses one):

  • StateOperator: (m, ctx) -> solve!(m; Assembly = true). The operator is solved only when a dependency changed, so the forms are always re-assembled (Assembly = false would also reuse the previous right-hand side).
  • LinearOperator: (m, b, ctx, stale) -> solve!(m, b; Assembly = stale): the matrix is re-assembled and factorised again only when a dependency changed.

Any other model (nonlinear, staggered, transient, or a StaticLinearModel with several right-hand sides) throws: the load stepping and the restart are modelling decisions, so pass solve = (m, ctx) -> solve!(m; stepping = …, RestartState = …). To use another solver (PETSc, an iterative solver with a preconditioner…) build the model with it, or pass your own solve.

HyperShape.Variables — Module
HyperShape.Variables

Design variables at three linked levels:

LevelObjectWhat it is
zOptVariableswhat the optimiser sees: one vector made of blocks, with bounds
xDesignFieldsdesign fields on the design mesh (cell-wise P0 or nodal P1)
θPhysicalFieldsphysical fields read by the weak forms at the quadrature points

Each level is built from the previous one, and only HyperShape writes them (in place). The maps x → θ (HelmholtzFilter, TanhProjection, Identity) are composed with ∘ in the mathematical order: TanhProjection(β = 1.0, η = 0.5) ∘ HelmholtzFilter(dΩ; rmin, ls) filters first and projects after.

Sensitivities travel backwards with design_gradient!: a linear form in δθ for each physical field gives the derivative with respect to z.

The vectors HyperShape assembles (load vector of a filter, sensitivities) use backend = :compiled by default (HyperFEMKernels: forms compiled once into threaded kernels) or backend = :lazy (Gridap's assembler); see HelmholtzFilter and PhysicalFields. Both give the same vectors up to rounding. The compiled backend is faster from tens of thousands of cells on, already with one thread, and scales with the threads (julia -t N); on meshes of about a thousand cells both take well under a millisecond per vector.

HyperShape.Variables.CellMean — Type
CellMean(dΩ; backend = :compiled)

Mean of the input field over each cell of the triangulation of dΩ: a P0 field, x̄_K = ∫_K x dΩ / |K| (with the quadrature of dΩ). On a measure over part of the domain the field is the mean on those cells and its integrals over the whole domain only see that part (Gridap's rule for fields on a sub-triangulation). After a filter it gives the density of codes such as top88 (xPhys = TF'·K⁻¹·TF·x): one value per element instead of the filtered field at the quadrature points. Linear in its input (a volume after it stays a linear constraint); no solve. backend assembles its vectors (:compiled, HyperFEMKernels, or :lazy, Gridap).

θ = PhysicalFields(x; ρ = CellMean(dΩ) ∘ HelmholtzFilter(dΩ; rmin, ls = LUSolver()))

HyperShape.Variables.HelmholtzFilter — Type
HelmholtzFilter(dΩ; rmin, order = 1, backend = :compiled, model_backend = <default>, solve = <default>, kwargs...)
HelmholtzFilter(op::LinearOperator, dΩ; backend = :compiled)

PDE filter (Lazarov and Sigmund, 2011): the filtered field ρ̃ solves a(ρ̃, v) = ∫(x v) dΩ for all v.

  • Short form (the usual filter): a(ρ̃, v) = ∫(r² ∇ρ̃⋅∇v + ρ̃ v)dΩ with r = rmin / (2√3), homogeneous Neumann conditions, on a Lagrangian space of degree order (continuous) over the triangulation of dΩ. kwargs go to HyperFEM's StaticLinearModel (for example ls = LUSolver(), ls = CGSolver(…) or a PETSc solver; without ls HyperFEM's default solver is used), model_backend is passed to it as its backend (who assembles the matrix; HyperFEM's default if omitted) and solve goes to the LinearOperator (default: assemble when the matrix changes).
  • General form: op is a LinearOperator whose model carries the bilinear form and the solver written by the user (Robin terms, Dirichlet conditions, anisotropy…). The bilinear form must be symmetric (the same solve gives the transpose for the sensitivities; checked by check_consistency) and the trial space may only have homogeneous Dirichlet values (checked).

The output is a field of the trial space of the filter (usually P1), also for a P0 design field. backend selects who assembles the load vectors of the filter: :compiled (default, HyperFEMKernels) or :lazy (Gridap); it is independent of the backend of the filter model, which assembles the matrix.

Cost: one assembly of a load vector and one solve each time the design changes, and the same for each sensitivity pulled back.

HyperShape.Functionals.Functional — Type
Functional(J, S::StateOperator; derivative, adjoint, scale, fields = nothing, parameters = ())
Functional(J, θ::PhysicalFields; derivative, scale, linear = false, parameters = ())

Objective or constraint.

With states (first form):

  • J(u, θ): value, a DomainContribution (∫(…)dΩ) or a number; u = get_state(S).
  • derivative(u, p, θ): total derivative with respect to the physical fields, ∂J/∂θ − ∂R/∂θ contracted with the adjoint p: a function δ -> ∫(… * δ)dΩ when θ has one field, or a named tuple of such functions ((ρ = δ -> …, E = δ -> …)), one per physical field it depends on.
  • S: forward StateOperator.
  • adjoint (mandatory): the adjoint state, usually AdjointOperator(S, model), which solves a(w, p) = ∂J/∂u[w] for all w (with a the tangent of the forward problem) on a space with homogeneous Dirichlet values; it must depend on θ and on S. Or :self for a self-adjoint functional (then p = u, with the sign in derivative; valid only when the Dirichlet values of the state are zero, which is checked here and when the gradient is computed).
  • fields: the physical fields θ. By default the only PhysicalFields among the dependencies of S; give it when S depends on none or on several.

Design only (second form, volume, perimeter): J(θ) and derivative(θ).

scale is mandatory: a positive number, :initial (the absolute value of the first finite evaluation; an error if it is zero) or 1.0 for no scaling. The value and the derivative are divided by it.

parameters: Parameters (or other objects with a state_version) that J reads directly, not through θ or a state (a weight that is continued, for example): the value is computed again when they change. A parameter read by a model goes in the dependencies of its operator instead; one read by a map, in the parameters of the PointwiseMap. linear (design-only form) declares a functional affine in z, checked when it is used as a constraint.

The value is kept until θ, a state or a parameter changes; the gradient is assembled at every call (one adjoint solve only when the design changed, one transposed filter solve per filter and one assembly per call).

If a state does not converge, functional_value returns NaN and functional_gradient! fills the gradient with NaN (the optimisers treat it as a failed trial).

HyperShape.Checks.check_consistency — Method
check_consistency(J1, J2, …; ctx = OptContext(:check), kwargs...) -> ConsistencyReport
check_consistency((name1 = J1, name2 = J2, …); ctx = OptContext(:check), kwargs...)

Checks, at the current design, that the derivatives the user wrote and the dependencies the user declared are consistent. The functionals must share the same optimisation variables z. Four kinds of checks:

  1. Gradient of each functional (Taylor test): J(z + hδ) − J(z) − h⟨∇J, δ⟩ must decrease with order 2 when h is halved. It covers DJform, the adjoint state and the maps x → θ at once.
  2. Design chain of each physical field (Taylor test of ½∫θ² through the maps alone, for every PhysicalFields reached from the functionals): if it passes and the gradient of a functional fails, the error is in DJform or in the adjoint, not in the maps.
  3. Symmetry of each filter: cᵀA⁻¹b = bᵀA⁻¹c for two random vectors, with the user's solve.
  4. Dependencies: at a perturbed design, value and gradient computed as usual are compared with the ones obtained after forcing every state and filter reached through the declared dependencies to assemble and solve again. A difference means that one of those operators depends on something it does not declare (for example a filter matrix that reads the design with depends = (), or a state listed in depends that under-declares its own dependencies). The check only changes the design: a Parameter read by a model but not declared is not detected (it does not change while the check runs). An object that no declared dependency leads to cannot be checked: its stale values go unnoticed when DJform treats it as fixed too.

Optionally, tangents = (S => (res, jac), …) adds a Taylor test of the tangent jac(u, du, v) against the residual res(u, v) of the state S at its current solution, in a random direction of its free values (the user's forms in Gridap's convention; for HyperFEM's load-factor forms pass res(Λ), jac(Λ)).

A Taylor test passes when two consecutive steps give an observed order of at least min_rate (both errors above rounding), or when every error is at rounding level while J does change along δ (a functional linear in z). It fails, as not tested, when J does not change along δ at all (for example a fully saturated projection): choose another direction or design. It fails as inconclusive when only the largest step gives an error above rounding (a nearly linear functional): try a larger h0. With h0 = 1e-2 a relative error of about 0.1 % in a gradient can still pass.

Keyword arguments:

  • ctx: passed to the solve functions (default OptContext(:check)).
  • direction: direction δ in z (default: random, scaled by the width of the bounds, zero within 1e-3 of the width from a bound).
  • h0: first step (default: 90 % of the largest step that keeps z + hδ inside the bounds, at most 1e-2).
  • steps = 5: number of steps of each Taylor test (h halved each time).
  • seed = 1: seed of the random directions and vectors.
  • min_rate = 1.8: observed order required.
  • rtol = 1e-8: relative tolerance of the symmetry and dependency checks (increase it with iterative solvers or Newton tolerances).

Cost: each forward state is solved at most steps + 4 times and each adjoint state at most 4 times (states shared by several functionals are solved once per design); each filter is solved once per step for checks 1 and 2, twice for check 3, and again whenever a gradient is pulled back. Use small meshes for nonlinear problems.

On return, z holds its initial values and the fields and states are brought back to it (one more solve of each state). The scales of the functionals are the ones they had; a scale = :initial not yet fixed stays unfixed (its functional is checked unscaled), fixed scales are used as they are. If a dependency check fails, the operators may hold matrices assembled during the check: fix the depends and build them again. Errors thrown by the user's forms or solves propagate (z and the scales are restored first).

HyperShape.PostProcess.FieldWriter — Type
FieldWriter(Ω, base; format = :vtu, precision = Float64, compress = false, async = Threads.nthreads() > 1,
            maxpending = 2, collection = nothing, resume_upto = nothing)

Fast writer of fields on the triangulation Ω (one cell type, cells of the dimension of the space; a part of a model is fine). The mesh is built once, continuous (one point per vertex of the grid, not one per cell and vertex as createvtk), and the values come straight from the degrees of freedom:

  • P0 fields as cell data; P1/Q1 (and the vertices of higher orders) as point data, scalar, vector or tensor, with their Dirichlet values; pointwise operations on them and on constants (θ.ρ, E ∘ θ.ρ, 1 - ρ); extend_field (points of the interface take the inside value).
  • Any other CellField (discontinuous fields, gradients, P0 mixed with P1, a function of x) is evaluated by Gridap at the vertices and averaged at the points, in the same file, with a warning once per field (slower).

format: :vtu (one file base_<index>.vtu per step, mesh included; with collection, a get_pvd collection, each file is added at its time once written) or :vtkhdf (one file base.vtkhdf with every step and the mesh written once; needs using HDF5, ParaView ≥ 5.12; the same fields at every step and increasing times). precision = Float32 halves the values (the points stay Float64); compress uses zlib (smaller, slower).

With async the values are copied and the file is written by another task: the caller waits only for the copy, at most maxpending steps are queued (then it waits for the disk). A collection lags behind by the queued steps. After an error of a write, later steps are not written and the error is thrown by the next write_fields or by close. close(w) waits for the pending writes (idempotent); wait(w) waits without closing.

resume_upto (VTKHDF): an existing file of the same mesh keeps its steps with time ≤ resume_upto, and the writer appends after them (a resumed optimisation). OptPostProcessor builds and closes these writers itself (see write_step).

HyperShape.PostProcess.OptPostProcessor — Type
OptPostProcessor(driver; every, filepath = nothing, initial = true, history = true, name = "optimization",
                 format = :vtu, precision = Float64, compress = false, async = Threads.nthreads() > 1,
                 maxpending = 2)

Post-processing of an optimisation: pass it to solve!(…; post). solve! calls driver(post, ctx) (written by the user, as the driver of HyperFEM's PostProcessor) with the fields, the variables and the forward state at the accepted design:

  • at the starting design (iteration 0, or the one of a resumed checkpoint), if initial. It costs no extra solve: the forward solve of the first iteration is done before it (so the user's solve sees ctx.iteration == 0 in that solve, and the forward column of the history counts it in no iteration). Not repeated when the collection already has that iteration, nor in a resumed run whose first iteration is a continuation jump;
  • after every accepted iteration that is a multiple of every (mandatory: one call per iteration can fill the disk; the multiples count from iteration 0, also in a resumed run);
  • at the end of the run (converged, stalled or maxiter) and when it fails (at the last accepted design, if the forward problem can still be solved there), when that iteration has not been written yet.

ctx is the OptContext (phase :optimization, ctx.iteration the iteration of the design). The adjoint state is still the one of the previous design. Nothing is called during check_consistency or for the trial designs of a line search. An error thrown by the driver stops the optimisation, except in the call after a failure (then it is reported and the failure is thrown).

filepath (a folder, created if needed; made absolute when the post-processor is built) enables the collection filepath/<name>.pvd (get_pvd, with the iteration as time; written after every entry, so it can be opened in ParaView during the run) and, if history, filepath/history.csv (the columns of OptHistory, written again at every call). Without filepath the driver writes what it wants (or nothing: a callback). Each solve! starts a new collection (files of an earlier run in the folder are left there, outside it); a resumed run keeps the entries up to the iteration of the checkpoint. The collection file is created with its first entry (none with format = :vtkhdf).

format, precision, compress, async and maxpending are the options of the FieldWriters that write_step builds (with async, the collection lags behind the loop by the queued steps): format = :vtkhdf (one file per triangulation and name with every iteration; needs using HDF5) suits large 3D runs, :vtu (default) any ParaView. The writers are closed (their pending writes finished) when solve! returns, fails or is interrupted. An error of a write during the run stops it (it is thrown by the next write_step); one that appears when the writers are closed at the end is logged with @error and solve! still returns its result. After a stall in a continuation stage whose last iteration was already written, the result of solve! is at the new stage but that iteration is not written again.

The driver can write with write_step (createvtk), add any file it writes itself (get_pvd(post)[ctx.iteration] = "file.vtu") or write nothing to the collection. Fields: post.filepath, post.every, post.iteration (of the current call) and post.problem (the Optimization being solved, set by solve!; it can be built before or after the post-processor).

post = OptPostProcessor(every = 10, filepath = "results/mbb") do post, ctx
  write_step(post, Ω, "rho" => θ.ρ, "x" => x.ρ, "u" => get_state(S))
end
solve!(problem, DensityMethod(OC()); maxiter = 300, post)

  • It keeps a copy of the design, value and derivative of its last gradient!: after a rejected step, the optimiser asks again at that design and gets them without solves.
  • A gradient that is not finite throws OptimizationFailure.

HyperShape.Methods.Optimization — Type
Optimization(; objective, constraints = (;))
Optimization(z; objective, constraints = (;))

Optimisation problem: minimise the Functional objective over the variables z behind it (given or not; when given they are checked) subject to the bounds of z and the named constraints g(z) ≤ 0, for example constraints = (volume = Vol,). The names go to the history (history.constraints.volume), the banner and the checkpoint. In phase 0, at most one constraint, a design-only functional: typically Volume(θ, dΩ; max_fraction) (volume of the physical density, nonlinear in z with a tanh projection) or Volume(x, dΩ; max_fraction) (volume of the design density, linear).

A constraint built as linear (Volume over identity or filter maps, or a Functional(…; linear = true)) is checked to be linear when the optimisation starts, and costs nothing in the loop (its vector is computed once). A nonlinear one is linearised at every step by the optimiser, which then corrects it with evaluations of the true constraint (one filter solve each, no forward solve): see OC and SiMPL.

The problem owns the context ctx (OptContext) that reaches the solve functions of the user.

HyperShape.Methods.OptimizationFailure — Type
OptimizationFailure(msg)

Thrown by solve! when the optimisation cannot continue: the forward problem does not converge at the current design (first iteration or right after a continuation jump), every attempt of a step was rejected, or a gradient is not finite (failed adjoint). z, the fields and the states are left at the last accepted design, and the checkpoint (if any) is written first. history holds the OptHistory up to the last accepted iteration and iterations its number (nothing and 0 when thrown outside the loop).

HyperShape.Methods.RejectStep — Type
RejectStep(; shrink = 0.5, max_attempts = 5)

What to do when the forward problem does not converge at the design proposed by the optimiser: go back to the previous design, call shrink! on the optimiser with shrink (0 < shrink < 1: OC multiplies its move limit) and try again, at most max_attempts attempts per iteration; then throw OptimizationFailure. RejectStep() is the default of solve! (with the defaults, the step can go down to 1/16 of the first one).

Optimisers that evaluate their trials (SiMPL) handle failures inside their line search, so for them this only applies if a step is accepted at a design that cannot be evaluated again.

HyperShape.Methods.StopCriteria — Type
StopCriteria(; objective_range = nothing, window = 10, kkt_tol = nothing, kkt_rtol = nothing,
             stationarity_tol = nothing, stationarity_rtol = nothing, change_tol = nothing)

Convergence criteria; each one is off unless given, and the first one met stops the optimisation (the reason in OptResult is the name of the keyword). With a Continuation they only act in the last stage, unless it was built with close_early = true (then a criterion met in an earlier stage ends that stage).

  • objective_range: range of the objective over the last window iterations of the current stage, (max - min), relative to max(largest |f| in the window, 1e-3 |f₁|) (f₁ the objective of the first iteration of the run, so an objective that tends to zero still converges), below this value. A range, not the difference between the ends of the window, so an oscillation does not pass for convergence.
  • kkt_tol: optimality measure of the optimiser below this value (absolute: units of the scaled objective). kkt_rtol: the same, relative to the one of the first iteration of the run (off if that one is not a positive number). Only with optimisers that compute it (SiMPL; with OC solve! throws before the first iteration).
  • stationarity_tol: the stationarity measure of the paper of SiMPL, S = ‖z − P(z − g)‖_M (stationarity!, computed by OC and SiMPL at the design before the step, so the run stops one iteration after it is met), below this value (absolute: it depends on scale and on the metric; with Euclidean() it depends on the mesh, use LumpedMass(dΩ)). stationarity_rtol: relative to the first finite value of the run. With a nonlinear constraint the projection uses the constraint linearised at z. OC computes it with the metric of DensityMethod (its step does not use it): give LumpedMass(dΩ) for a value independent of the mesh, comparable with SiMPL.
  • change_tol: maximum(abs, Δz) of the step below this value. With a tanh projection it is rarely reached.

The tolerances are not checked at the first iteration of a stage (after a continuation jump the first step restores feasibility and its measures say little); objective_range needs window iterations of the stage.

Gridap.Algebra.solve! — Method
solve!(problem::Optimization, method::DensityMethod; maxiter, on_failure = RejectStep(),
       stop = default_stop(optimizer), continuation = nothing, checkpoint = nothing, post = nothing,
       monitors = (;), resume = nothing, verbose = 2, io = stdout) -> OptResult

Runs the optimisation from the current values of z. Mandatory: maxiter (total iterations, resumed ones included). Optional: on_failure (RejectStep, default RejectStep(shrink = 0.5, max_attempts = 5)), stop (StopCriteria; default default_stop: range of the objective below 0.1 % over 10 iterations of the last stage; stop = nothing runs maxiter iterations; or a function (or callable object) (info, history, ctx) -> Bool of the user, checked after every accepted iteration, with the StepInfo of the step (info.f is the objective before it), the OptHistory up to this iteration (a copy) and the context: true stops with reason :custom, under the same rules as StopCriteria (only in the last stage of a Continuation unless close_early; with a nonlinear constraint, only when it holds to the tolerance of the optimiser)), continuation (Continuation), checkpoint (Checkpoint), post (an OptPostProcessor: its driver is called at the starting design, at the accepted iterations that are multiples of every, at the end and after a failure, with the fields and the forward state at the accepted design; the adjoint state is still the one of the previous design) and monitors (a named tuple of monitors, such as (grey = Grey(θ, dΩ),): their values, see monitor_value, go to the history, the table and the closing line), resume (the folder of a Checkpoint or the result of load_checkpoint), verbose and io. An OC whose move is continued by continuation gets its own move back when solve! returns or throws; the other continued parameters keep the values of the last stage.

Screen output (verbose, default 2, printed to io): 0 nothing; 1 a banner (variables, constraint, metric, continuation, stopping criteria and failure handling, each marked when it is a default), the events (continuation jumps, rejected steps, stalls, a scaled start), a closing ✓/⚠/✗ line and a summary of solves and time; 2 also a row per iteration: objective, its relative change, constraint (red above 1e-3), optimality measure kkt, stationarity measure S, change of z, step, multiplier, continued parameters, monitors, forward, adjoint and filter solves, and time. true is 2, false is 0. The summary counts every solve of the call (those of rejected or stalled trials, the setup and the final synchronisation included).

With a checkpoint, an exception that is not an OptimizationFailure (an error in a solve, post or monitor function of the user, an interruption) writes a checkpoint at the last accepted design (history included) and is then rethrown; an OptimizationFailure writes its own.

If the starting design (not a resumed one) violates the constraint, it is scaled towards the lower bound, z = lb + t (z − lb) on the entries the constraint acts on (a linear constraint: so that it holds with equality; a nonlinear one: with t found by regula falsi so that -1e-6 ≤ g ≤ 0); t is returned in result.start_scaling and reported as an event when verbose ≥ 1. At a continuation jump the design is not touched: an optimiser that finds it infeasible restores feasibility in its next step.

Each iteration: the optimiser takes a step from the current design; the loop evaluates the new design (no solve when the optimiser already did, as SiMPL); if the forward problem does not converge there, the design is restored, the step shrunk and tried again. Solves per iteration: OC one filter, one forward, one adjoint (none for a self-adjoint functional) and one transposed filter; SiMPL one filter and one forward per trial of its line search (usually one), one adjoint and one transposed filter; one more forward after each continuation jump. A linear constraint costs nothing in the loop (its vector is computed once at the start); a nonlinear one costs, per step, one transposed filter for its derivative and one filter per correction (see OC and SiMPL), and no forward solve. With a nonlinear constraint the run only converges when the constraint also holds to the constraint_tol of the optimiser.
