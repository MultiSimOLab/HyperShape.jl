Benchmarks

The benchmark bank runs HyperShape on fixed problems with every method that applies and reports every run in one fixed table, so that methods, discretisations and versions can be compared on the same footing. It lives in the folder validation/ of the repository, outside the package: the cases are scripts written with the public API, and the shared helpers (validation/common/) are scripts included by them, not part of HyperShape. The Validation page discusses each case against its reference; this page describes the bank, its table and the rule for comparing methods, and collects the tables of the cases that exist today.

Running the bank

julia --project=validation -e 'using Pkg; Pkg.instantiate()'
julia --project=validation -t 4 validation/run_all.jl                    # every case, about 17 min
julia --project=validation -t 4 validation/run_all.jl mbb_top88 bridge_takezawa   # some of them

run_all.jl runs each case script in its own Julia process (with the threads of the calling one), keeps its output in results/<case>.log and joins the tables of the cases into results/report.csv and results/report.md. Each script can also be run alone (julia --project=validation -t 4 validation/<case>.jl); it prints its own table and then writes its rows of the fixed table to results/<case>.csv and results/<case>.md. The folder is validation/results (not versioned) or ENV["HYPERSHAPE_RESULTS"]. A case fails when its script stops with an error or one of its checks does not hold (the script exits with code 1); run_all.jl reports it, still runs the others and exits with code 1. Times are measured after runs on small meshes that compile every variant of the case, with the machine free (one run at a time, load average checked before); the tables carry the machine, the threads, the Julia version and the commit (+dirty when the tree had changes).

The table

One row per run. A reference (a port of another code, a code run in Octave, a published value) has its own row, first, with the measures of its design when its design is available, and "–" for what it does not have.

columnmeaning
case, variantthe problem and its mesh; the design variables, the method and the options that are not the defaults
Jthe objective of the method on its final design (result.objective; the cases use scale = 1.0)
J_binthe objective of the final design read as 0/1 per cell: solid where the cell mean of the physical field is at least ½, with the same mesh, loads and supports and the material law E = Emin + (1 − Emin) χ (plain Gridap, binary_evaluator)
ref, vs refthe reference value of the case and the deviation from it, with the column it is compared with (J or J_bin)
Vthe volume fraction that the constraint sees (vf · (1 + g), from the history of the constraint volume, a Volume(…; max_fraction = vf) with its default scale)
V_binthe fraction of solid cells of the 0/1 design
greySigmund's measure of grey of the cell means, mean of 4χ(1 − χ) (0 for a 0/1 design; with a level set and Ersatz() it only sees the cut cells)
perimeterof the 0/1 design, in domain units: the interior faces between a solid and a void cell times their length (an area in 3D). A staircase measure: comparable between methods on the same mesh; under refinement it tends to the ℓ¹ length of the boundary, not to the Euclidean one
holesinterior holes of the 0/1 design: connected components (by faces) of void cells that do not touch the boundary of the domain; in 3D, closed cavities. Specks of one or two grey cells count as holes
iterationsaccepted iterations, with the status and the reason of the stop
solvessolves of the state, of the adjoint, of the filter (forward and transpose) and of the method's own step, summed over the history (forward/adjoint/filter/step_solves): the step of reaction–diffusion solves with its diffusion operator (one per iteration, one per implicit substep of the double well, none with the explicit scheme); a density method has none (0)
timeseconds of solve!, without compilation
time ÷ state solvesthe time divided by the number of state solves: the cost of the method per state solve on that mesh and machine, with everything else included (filter, the step of reaction–diffusion, the evaluations of the volume, monitors such as the binary compliance of levelset88). It is not the time of one solve: the solves column counts each kind, the time of each kind is not measured

Comparing designs

The objective that a method optimises is not comparable between methods: SIMP with a filter keeps grey material, a level set with Ersatz() has cut cells, a density of reaction–diffusion has a diffuse interface. The common measure is J_bin, the same problem evaluated with the design read as 0/1 per cell. The tolerances of the bank are:

  • against another code with the same discretisation and formulation (a published value of it or a port): J within 1 %. Cases: the MBB with the cell mean and OC as top88 against Fig. 4 of Andreassen et al. (2011), the PDE filter (+0.00 %); SiMPL with the sensitivity of the authors' code against their tables 1 and 2 (+0.00 %);
  • against a published value obtained with another discretisation or formulation: J within 5 % (SiMPL with the exact sensitivity and OC: −0.40 % to −0.99 %). The bridge of Takezawa et al. uses 3 %, the tolerance decided for the double well (the default reproduces 23.3 within 2.6 %);
  • between methods of HyperShape on the same mesh, and against another code or method run on the same mesh (top88.m with its convolution density filter, ft = 2, against the Helmholtz filter with r = rmin/(2√3); levelset88): J_bin within 5 %.

Each script checks its own rule and exits with code 1 when it does not hold (the 3D cantilever and the mesh study of the double well have no reference value: their checks are consistency, symmetry, convergence and volume, and J in the measured intervals).
